# The UI pack: design sources

Everything the touch interface is built from lives here: tokens, icons, components, screens, strings. Commands
in this file run from `app/`. One command rebuilds the pack:

```sh
python3 mobile-ui/design/build.py            # build/ui-pack/
python3 mobile-ui/design/build.py --check    # fails when a source, a baked texture or a spec is stale or inconsistent
```

The UI runtime is the engine's RmlUi library (`engine/src/libs/ui`); the application only hosts it. No UI look or
layout is written in Java.

## Constraints

- Landscape only. The UI uses the real display density: the viewport is the screen in dp (phones about 780–960 ×
  360–430, tablets 1024 × 768 and 1280 × 800). 915 × 412 is only the design artboard; nothing is positioned or sized
  from it.
- Text is shaped by FreeType without HarfBuzz: Latin and Cyrillic only.
- No accessibility tree. Typing is avoided; where it remains, the host shows a native editor over the field
  (`Config::on_text_request` / `Host::SubmitText`, Android `UiTextEditor`).

## Layout

| Path | What | Edited by hand |
|---|---|---|
| `tokens.json` | colours, type, sizes, spacing, radii, timings, material numbers | yes |
| `icons.json` | the icon definitions: SVG elements per symbol, an optional accent layer (one source for the game) | yes |
| `components/<name>/spec.json` | props, states, sizes, behaviours of one component | yes |
| `components/<name>/template.rml`, `style.rcss` | its markup and look in the game | yes |
| `hud-layout.json` | where HUD elements sit in each scene (edge anchors from the safe area) | yes |
| `base.rcss`, `overlay.rml` | document base rules, toast and tooltip layer | yes |
| `screens/<name>/spec.json`, `template.rml`, `style.rcss` | game screens and screen parts (`<s-…>`) built from the components; filled by the engine's screen routing (engine `src/libs/ui/src/screens/README.md`) | yes |
| `screen.rml` | the document a game screen is mounted into | yes |
| `scripts.json` | the interface scripts the engine attaches to the game's program, in order (`../PROGRAM/interface/touch`): file, `core` (its failure stops the start), requirements on the game, the screens it provides (capability, interface, pack screen, the nodes it reads); engine `src/libs/ui_host/README.md` | yes |
| `capabilities.json` | the one list of the interface's capability ids; `build.py --script-header` makes the scripts' `capabilities.h` from it (packaged with the scripts) | yes |
| `hud.rml` | the document of the in-game HUD (`<s-hud>` layer) | yes |
| `strings/<lang>.json` | UI strings, one flat `{key: text}` table per shipped language (ru, en, de, es, fr, it) | yes |
| `gallery/*.rml` | the debug gallery: every component in every state | yes |
| `fonts/` | Noto Serif, Great Vibes (SIL OFL 1.1, licence texts alongside) | no |
| `textures-src/` | oak (screen ground) and lapis (header plate): materials made for this project, no game assets (provenance: NOTICE); `bake.json`: the static shade baked into each | no |
| `textures/` | generated by `bake_textures.py` (Pillow) from `textures-src/`: the pictures with their shade, so the screen ground and the header plate are one fill each; `baked.json` lets `build.py` fail on a stale bake without Pillow | **no** (run `bake_textures.py`) |
| `images/` | pictures made for this project, shipped as they are (PNG with alpha, at 3x their size in dp): `dustoff.png`, the studio's wordmark on the About screen (see NOTICE); `build.py` fails on a picture no source names or a name with no picture | yes |
| `app/build/ui-pack/` | generated: the pack the APK ships as `assets/ui` | **no** |

Level 1 (tokens and icons): a token or an icon changed here changes the game pack after one
`build.py` run.

The build fails loudly rather than guessing: an unknown token, a component tag that has
no spec, a prop a component does not have, an enum value outside its options, an icon id
that is not in the icon set (in gallery pages, component templates, spec constants and
`hud-layout.json`) and a raw colour value are all errors.

Level 2 (specs and HUD layout): `spec.json` is the contract of a component. A `json` prop that a script screen fills
names its structure in `shape` (a type, `{field: shape}`, or `[item shape]`): the script's view is converted by it. The game reads `components.json`
and `hud-layout.json` from the pack at run time.

**Licence rule.** No game picture is ever stored here or in the APK. Portraits, item
art and sail emblems are `<c-game-image texture=… cell=…>` slots filled at run time
from the player's own game files. The sources here are GPL-3.0-or-later like the rest of
the application; the fonts are SIL OFL 1.1 (see the repository's NOTICE).

## UI strings

No text the player reads is written in a template or in C++. It lives in
`strings/<lang>.json` under a dotted key (`trade.price`); templates use
`{{ tr('trade.price') }}`, screens `bindings.Text("trade.price")` (engine
`src/libs/ui/src/screens/README.md`). The game's language chooses the table. The build
fails when a language lacks a key another has, or when a template or the engine's UI code
names a key that is not defined (the engine's code is read from `engine/`; `--engine-root`
names another tree, `--no-engine-check` skips the engine-key check explicitly). Texts the game itself sends
(captions, names, prices) are not in the table. The few texts the Android host shows itself (download
notifications, the look area's accessibility label, two toasts, the interface failure dialog) are the `host.*`
keys, read by `MenuText`; nothing checks their use, so remove a key with the Java that names it. A new language
also needs its name in `GameLanguage.code` and `GameLanguage.name`.
Components never contain player-facing literals: text props default to `""` and the
template falls back to `tr('…')`; the spec marks that with `"defaultKey"`, the
key of its text in `strings/`.

## Tokens in sources

`@{group.name}` works in `.rcss`, `.rml` and `spec.json`:

- `@{color.wood}` → `#16272d`; `@{color.brassLine/.6}` → the colour with alpha 0.6
  (written as RCSS 0–255 alpha).
- `@{size.touch}`, `@{type.body}`, `@{space.md}` → the number; write the unit yourself (`dp`).
- `@{spec.height.md}` inside a component's own files → a value of its `constants`.
- `@{…|json}` → the JSON of a whole table.

One colour value has exactly one token; `build.py` refuses duplicates.
Component sources, `base.rcss`, `overlay.rml`, gallery pages and `hud-layout.json` hold
no raw colour values (`#rrggbb`, `rgba(…)`): the build fails on one. When a value truly
cannot be a token, mark that line with a `/* colour-literal: <reason> */` comment.

## HUD layout and the safe area

`hud-layout.json` places every HUD element of a scene by an edge pair, `anchor =
"<left|right|center|stretch>-<top|bottom|center|stretch>"`, with offsets in dp measured
from the **safe area** (the system bars; the display cutout is ignored:
elements may lie under the camera): `left`/`right`/
`top`/`bottom` name the edge, `x`/`y` shift from the centre line, `stretch` gives both edges
so the box follows the screen (columns that wrap, the sail lever that shrinks on a short
phone). Nothing is placed from the artboard origin: the viewport is the real screen in dp
(phones about 780–960 × 360–430, tablets 1024 × 768 and 1280 × 800); physical sizes stay
and the extra space goes to the free centre of the HUD and to wider lists in menus. `props` are static, `sample` holds
example live values for the gallery. `build.py` validates the anchors, adds the ready
position style `rcss` to every element of the pack copy and generates one gallery page
per scene (`gallery/hud-<scene>.rml`, pack only) from the same data, so the page is the
layout. Elements go inside `<c-scene>`, whose HUD layer is the safe area; `<c-screen>`
keeps its header and content inside it too.

In the game the same elements are mounted into `hud.rml` (`<s-hud>`, the transparent
safe-area layer) by the engine's HUD mount (engine `src/libs/ui/src/hud`): the scene of the
gameplay mode, live props from the game's state channels, an element left out by the game
not mounted at all. `behavior` gives an element one more touch behaviour (`hold`: reports
down / up; `swipe`: a drag picks a move, configured by `data` → `data-swipe-*`);
`"gallery": false` keeps an element that only appears on demand off the gallery page.
HUD parts that are not single components live in `screens/hud-*` (`s-hud-sheet`, the land
action sheet; `s-hud-moves`, the sword-move wheel on `<ui-wheel>`).

No two elements of a scene may overlap on any of the build's check screens, with every party list at its
maximum; `build.py` fails on any overlap. Allowed are an `overlay` (drawn over the others for a moment, the
sword-move wheel), elements that `replaces` the other (never shown together), and the zone of a floating control
listed before the elements it lies under (the land move stick, the deck walk stick): drawn under them, it takes
only the touches they leave, and its control at rest must stay inside its zone and clear of them, but for the event
lines, which come and go. A zone marked `clear` (the helm: a thumb beside a button must not take it) is checked as a
whole box, but for the elements it names in `under`, which are drawn over it and keep their own touches. A zone
whose `offWith` names another element is off while that one is shown; then only the two controls at rest must be
clear of each other.

The host reports the insets with `Host::SetSafeArea(left, top, right, bottom)` (dp);
templates can read them as `safe.left` … `safe.bottom`. `storm_ui_shot --safe 48,0,24,0`
renders a page with insets.

## A component

`spec.json`:

```json
{
  "tag": "c-button",
  "props": { "variant": {"type": "enum", "options": ["primary", "secondary"], "default": "secondary"},
             "disabled": {"type": "bool", "default": false},
             "items": {"type": "json", "default": []} },
  "classes": { "done": "hold && holdProgress >= 100" },
  "behaviors": ["press"],
  "constants": { "height": {"sm": @{size.buttonSm}, "md": @{size.buttonMd}} }
}
```

- Prop types: `text`, `bool`, `int`, `number`, `enum`, `json` (arrays and objects).
  In RML a prop is the kebab-case attribute (`holdProgress` → `hold-progress="60"`);
  `json` props take JSON text (`items='[{"label":"A"}]'`); `props='{…}'` sets many.
  A bool attribute is true unless its value is `false`, `0` or `no`.
- Root classes: a true `bool` adds its kebab name (`disabled`), an `enum` adds
  `name-value` (`variant-primary`). `"class": false` on a prop turns that off.
  `classes` adds computed ones. Behaviours add `pressed`, `done`, `active` while live.
- Layout boundary: `"constants": {"layoutBoundary": true}` on a component, or the attribute
  `rmlui-layout-boundary=""` on a template element, says that the layout around it decides
  its width (and position) and that its contents stay inside it. A change inside it then lays
  out only it (the whole screen only if its size came out different). Use it for bars of fixed
  height (C-Header), list rows and fixed panels, never for an element sized by its contents.
- Box from a prop: `"constants": {"boxSize": "size"}` makes that number prop the component's
  width and height in dp (C-Icon), so flex rows measure it without formatting its content.

`template.rml` is the inner markup. It is rendered again whenever a prop changes.

- `{{ expr }}` escaped text, `{{{ expr }}}` raw RML.
- `<t-if test="expr">…<t-else/>…</t-if>`, `<t-for each="items" as="it">…</t-for>`
  (also `it_i`, `it_last`).
- Expressions: props by name, `spec.<constant>`, `children` (true when the component
  has content), literals, `! - + * / %`, comparisons, `&& ||`, `a ? b : c`, and
  `or(a, b)`, `len`, `num` (thin-space thousands), `str`, `int`, `round`, `min`, `max`,
  `clamp`, `abs`, `in(x, 'a', 'b')`, `pick(key, 'a', 1, 'b', 2, fallback)`, `starts`,
  `contains`, `ends`, `replace(s, from, to)`, `split(s, sep)`, `range(n)`, `digits('1 500')`,
  `has(obj, 'k')`, `is_object`, `is_array`, `is_string`, `json(x)` (to pass a structure
  to a nested component: `props="{{ json(it.q) }}"`), `image_kind(image, icon)` (see below).
- The element with a `slot` attribute receives the component's children.
- Components nest by tag: `<c-icon icon="{{icon}}" size="18"/>`.

Row images: list rows, tiles, table cells, trade rows, object headers and ship cards take
one `image = {kind: icon|token|item|portrait|emblem, icon, enamel, texture, cell}`; a bare
`icon` is the shorthand for `{kind: 'icon'}`, and no image and no icon means no lead.
`image_kind(image, icon)` tells which one it is; `<c-row-image image icon size icon-size tone
surface disabled>` (a runtime helper) draws it as a C-Token, a
C-GameImage slot or a bare C-Icon. Every component takes `selected`, and `disabled` with a
`reason` that is shown as a toast on tap, never drawn.

Behaviours and the marks they read (engine `src/libs/ui/src/behaviors.cpp`):

| behaviour | marks in the template | reports |
|---|---|---|
| `press` | whole component, or parts with `data-action="verb"` (+ `data-value`, `data-disabled`, `data-reason`, `data-hold`); set `constants.pressRoot: false` when only parts are pressable. A part may also carry `data-step="±n"` / `data-set="n"` (+ `data-prop`), `data-toggle="prop"`, `data-select="arrayProp" data-index="i"`: the component changes its own prop at once. `disabled` + `reason` → toast on tap. Prop `hold` = hold-to-confirm with `<ui-ring>` (or, with `constants.holdMode: "tooltip"`, a long-press tooltip showing `tip` or `title`). | `verb value` |
| `range` | `data-range="value"` on the track (props `min`, `max`, `step`; `data-inset` = knob half-width in dp); `data-range-knob` on the element the template places at the value: while the finger drags, the runtime keeps it under the finger with a transform (a value has steps, the finger has none) | `change`, `commit` |
| `stick` | `data-stick="x"` or `"xy"` on the travel area, `data-knob-size`. Prop `floating`: the component's box is a zone, the stick comes to the finger that lands anywhere in it (`atX`/`atY`); with `floatAxis: "y"` only up to its height (never below its rest), keeping its rest left (the helm). Prop `fixed` turns the zone off for a while (the sea helm in first person on deck): the stick works only where it rests and the rest of the zone lets touches through | `change` |
| `lever` | `data-lever="steps"` or `"continuous"` on the rail, `data-steps`, `data-knob-size` | `change`, `hold up/down` |
| `fit` | none: the component gets the class `roomy` when its content is cut in the layout its style gives without it (its style for `.roomy` gives more room); measured again after each render and each change of its height | nothing |

Elements drawn by code: `<ui-icon name size>` (use `c-icon`), `<ui-ring value shape="rect|circle" thickness>`,
`<ui-paper seed>` (aged parchment sheet), `<ui-clamp lines min-size text>` (text in 1–3 lines; with
`min-size="@{type.min}"` it steps down to that size before it is cut with an ellipsis: every short
label — tile names, stat labels, the header's subject, bar labels — uses it, so it fits at phone
width in every language; a word may break after a hyphen inside it; plain `text-overflow: ellipsis` only for long
free text),
`<ui-game-image texture cell grid>`.

## RCSS is not CSS — what differs

- Units: `dp` everywhere (never `px`). No `calc()`, no `inset`, no CSS grid, no `%` radius.
- A flex container lays out **elements only**: wrap bare text in a `<div>`.
- `max-width: 100%` inside an auto-sized parent collapses; use `flex: 0 1 auto; min-width: 0; overflow: hidden`.
- Backgrounds: `background-color` plus `decorator: linear-gradient(…), radial-gradient(…)`
  (first listed is on top, as in CSS; gradient stops take one position each).
- `box-shadow: <colour> <x> <y> <blur> <spread> [inset]` — colour first.
- Text shadow: `font-effect: shadow(0dp 1dp #000)` or `glow(2dp #000)`.
- `border: 1dp #colour` (solid only). `transform`, `opacity`, `transition`, `@keyframes`
  + `animation: 0.8s linear infinite name` work.
- Tabular figures: Noto Serif digits are already equal-width; nothing to set.
- Descendant selectors reach into nested components (`c-dialog .text` also hits
  `c-button .text`): style your own parts through child chains (`c-dialog > .box > .text`).
- Noto Serif has no `→` or `✕`: use icons (`chevron-right`, `close`).
- Every `div` needs no rule, but custom tags are inline by default: give each component
  a `display` in its `style.rcss`.

## Checking a component

```sh
../engine/build/ui-host/storm_ui_shot --pack build/ui-pack --doc gallery/button.rml \
    --size 915x412 --density 2 --out build/button.png \
    --script "down 1 660 88; wait 0.5; shot build/held.png; up 1 660 88"
```

(`cmake -S ../engine/src/libs/ui -B ../engine/build/ui-host -G Ninja && cmake --build ../engine/build/ui-host`
builds the tool.) `--only name,name --pack <dir>` builds a partial
pack while working on one component.
